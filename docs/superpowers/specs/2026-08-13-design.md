# Urd: design

Date: 2026-08-13
Status: approved, pending implementation plan

Urðr, eldest of the Norns, is "that which has become". She sits at the well and
measures what has happened. This tool does that to a Jira project's ticket
history.

## Purpose

A local tool that mirrors one Jira project's activity into DuckDB and renders a
single self-contained HTML report. It serves four readers from one page:

1. **Flow health for a team lead**: where work piles up, what is aging.
2. **Reporting outward to stakeholders**: delivered versus open per release.
3. **Retro material for the team**: rework, carry-over, cycle time trend.
4. **Individual contribution evidence**: throughput, review load, handoffs.

The report is shared as the HTML file itself. There is no server, no per reader
variant, and no scheduled run.

## Why not Jira's own reports

Jira draws velocity, burndown, control and cumulative flow charts already. Three
gaps justify a separate tool:

- **Transition authorship is not exposed in any built-in report.** So review load
  and handoffs, which are most of a reviewer's contribution, are invisible. This
  is the largest gap and the hardest to work around.
- **Nothing in Jira reports coverage.** A chart over a field that a third of the
  team fills looks identical to one over a field everybody fills.
- **Jira's reports are board scoped, one per page.** A component slice of a
  project needs a board whose filter happens to match, and the result still
  cannot be put on one page or handed to someone as a file.

Anything Jira already does well is out of scope. In particular, no burndown.

## Configuration

Nothing instance specific is compiled in. There are no defaults naming a site, a
project, a component or a status, and no config file in the repository.

Scope is given once on the command line and remembered:

```
urd sync --site example.atlassian.net --project PROJ --component TEAM --since 2026-01-01
urd sync                       # thereafter, scope read from sync_state
```

The scope on record is printed in the report header, so a report can never be
mistaken for one covering a different slice. `--project` and `--component` accept
comma separated lists, because joining a list into JQL is the same code as
joining one value. Omitting `--component` scopes to the whole project.

Credentials come from the macOS keychain:

```
security add-generic-password -s urd -a <email> -w   # once, by hand
security find-generic-password -s urd -w             # by the tool
```

`URD_TOKEN` and `URD_EMAIL` override, for CI or debugging. No token in a
dotfile, no token in the repository.

### What must never enter the repository

The report output, the DuckDB file and any captured API response all contain
real ticket keys, display names and email addresses. All three are gitignored
from the first commit. Test fixtures are hand written and synthetic rather than
captured and scrubbed, because scrubbing is a step that only has to be forgotten
once. See `tests/fixtures/README.md`.

Status names are configuration, not constants. `STATUS_ORDER` and the review
status are supplied by the user, so a real workflow's status names are not
baked into the source either.

## Scope of data

One project, optionally filtered by component, bounded by `updated`:

```
project = PROJ AND component = TEAM AND updated >= <since>
```

People are discovered from the data. Whoever appears as assignee, reporter or
transition author within scope is in the per-person charts, so a team change
needs no configuration edit and no roster file.

Bounding on `updated` rather than `created` is deliberate: long lived tickets are
still active and would be missed by a `created` bound. The full changelog arrives
with each issue, so transitions from before the window are available for cycle
time even when the ticket predates it.

Membership is evaluated at sync time against each ticket's current component. So
when a ticket is tagged retroactively, its full history joins the report rather
than only the part after tagging. That is the wanted behaviour, but it makes the
report a current-ownership view of history rather than a point-in-time one.

### Why scope is not "follow the people"

The obvious alternative is a second JQL arm for a roster of assignees across
several projects. It was designed, then measured, then deleted, and the reasoning
is worth keeping:

- **Work you request from another team is assigned to that team.** Following
  people therefore imports the other team's flow while adding almost none of
  your own. Measured on a real instance, the roster arm across two neighbouring
  projects returned nothing at all for the author over seven months.
- **Service desk projects do not share a workflow with software projects.**
  Statuses like "waiting for customer" have no position in a development status
  order, so `STATUS_ORDER`, rework and cycle time would all need per project
  definitions. One project keeps one workflow.

The cost of this choice is that work outside the project is invisible. That is
accepted and measurable, not ignored: compare the report's headline count against
a plain project wide count to see what the component filter excludes.

## Architecture

```
urd sync    →  Jira REST v3  →  raw_issues(key, updated, json)
urd derive  →  raw_issues    →  issues / changes / issue_sprints
urd report  →  derived       →  report.html
```

`sync` is the only step that touches the network. `derive` is pure, offline and
idempotent, so a changed metric definition costs a second rather than a refetch.

This is the central decision. The network is the only expensive part, and metric
definitions are the part that changes: you will argue with yourself about whether
cycle time starts at first-in-progress or at creation, and this makes that
argument cost a second.

### Files

| File | Contains | Changes when |
| --- | --- | --- |
| `urd.py` | CLI, sync, derive | Jira changes |
| `charts.py` | The chart specs: SQL, title, kind, caption | A metric changes |
| `render.py` | SVG generation, HTML assembly | Rarely |
| `test_urd.py` | Checks against synthetic fixtures | Each change |

The split exists so that adding a chart requires SQL and nothing else. With six
charts a single file would have been right; with sixteen, the chart spec list is
the one abstraction that pays for itself.

Style: stdlib plus one dependency, argparse, no framework. Run via
`uv run --with duckdb`, so there is no venv to maintain.

### Sync rule

One rule, applied per issue key:

> Fetch it if the key is absent, or if its `updated` value differs from the
> stored one.

This handles both directions at once, newer changes and an earlier `--since`,
with no window arithmetic. Two passes:

1. JQL search for `key` and `updated` only, 100 per page via `nextPageToken`.
2. `GET /rest/api/3/issue/{key}?expand=changelog&fields=<list>` for each key the
   rule selects.

One request per changed issue, so a first backfill is one request per issue in
the window and a daily sync is a handful. Fetching the changelog per issue rather
than via `expand` on the search endpoint avoids depending on whether the enhanced
JQL search endpoint honours `expand=changelog`, and brings fields and history in
one request instead of two.

`sync_state` holds the scope, the earliest `--since` synced, and the last
successful sync time, so a bare `urd sync` continues correctly.

Failure handling: a failed issue fetch is retried once, then recorded in
`sync_errors` and skipped. `sync` is resumable, so a killed backfill is continued
by running it again. Partial data is never presented as complete: the report
header carries the sync timestamp and any error count.

### Fields fetched

`summary, issuetype, status, statuscategorychangedate, priority, labels,
components, assignee, reporter, created, updated, resolutiondate, resolution,
parent, fixVersions, timespent, timeoriginalestimate, worklog`, plus the resolved
Story Points and Sprint custom field ids.

`worklog` is fetched and nothing derives from it, because cycle time from the
changelog is a better effort proxy than logged time that only some people record.
It rides along free on a request already being made, so a future logged time
chart needs no refetch. A `ponytail:` comment records that.

### Custom fields are resolved by name, never hardcoded

Field ids are read from `/rest/api/3/field` and cached in a `fields` table. No
hardcoded `customfield_10016`.

This is not tidiness. Story Points is a per instance custom field, and JQL
emptiness predicates on it cannot be trusted: on a real instance,
`"Story Points" is not EMPTY` and `"Story Points" is EMPTY` returned every issue
and no issues respectively, a contradiction, while the field id commonly cited
for it was null on every issue sampled. So `derive` resolves the id, measures its
null rate, and reports both. Charts depending on an optional field render only
when its null rate clears the chart's threshold.

## Data model

`raw_issues` is the source of record. Everything else is derived and can be
rebuilt from it offline.

| Table | Columns | Notes |
| --- | --- | --- |
| `raw_issues` | `key`, `updated`, `fetched_at`, `json` | Written only by `sync` |
| `sync_state` | `site`, `project`, `component`, `earliest_since`, `last_sync_at` | One row, the scope on record |
| `sync_errors` | `key`, `at`, `error` | Cleared on successful refetch |
| `fields` | `id`, `name`, `null_rate` | From `/field`, refreshed on sync |
| `people` | `account_id`, `display_name` | Observed in the data, no roster |
| `issues` | key, project, type, status, status_category, assignee_id, reporter_id, created, updated, resolved, story_points, timespent_s, parent, fix_versions, labels, components | One row per issue |
| `changes` | `key`, `ts`, `field`, `from_str`, `to_str`, `author_id` | Every changelog item, not only status |
| `issue_sprints` | `key`, `sprint_id`, `sprint_name`, `state`, `start`, `end`, `ordinal` | From the Sprint field array |

Two modelling choices worth stating:

**`changes` covers every changelog field, not only status.** Status transitions
become a view over it, and assignee history comes free, which is what the handoff
matrix needs. One general table is both simpler and more capable than two
specific ones.

**Sprint membership comes from the Sprint field array, not the changelog.** The
field holds every sprint an issue has belonged to, in order, so carry-over is
`ordinal > 1` with no changelog string parsing. The changelog's Sprint items
carry comma joined names rather than ids and are not needed.

### Views

- `transitions`: `changes WHERE field = 'status'`.
- `status_durations`: `LEAD(ts) OVER (PARTITION BY key ORDER BY ts)` against
  `transitions`, with the open interval closed at `now()` for the current status.
  This window function is why DuckDB earns its place over SQLite here.

### Metric definitions

Stated once so the charts do not each invent their own:

- **Lead time**: `created` to `resolved`.
- **Cycle time**: first transition into the first in-progress status, to
  `resolved`. Tickets that never entered it are excluded and counted in the
  coverage denominator.
- **Aging**: for open issues, `now()` minus the timestamp of the last transition
  into the current status.
- **Rework**: a transition where `STATUS_ORDER.index(to) < STATUS_ORDER.index(from)`.
  Statuses absent from `STATUS_ORDER` rank last and are listed by `derive`, so
  the order can be corrected rather than silently misread.
- **Throughput**: issues reaching a `Done` status category, counted per week by
  transition timestamp rather than `resolutiondate`, so a reopened ticket counts
  once per closure.

## Charts

Sixteen, in four sections on one page. Every chart carries a coverage denominator
in its subtitle ("192 of 533 tickets"). Any chart below its coverage threshold
renders as a warning strip stating what is missing, never as an empty or
misleadingly partial plot.

Default threshold is 70% of tickets in scope, overridable per chart. The two
points charts use 50%, matching the null rate rule. Charts 1, 2, 6, 8, 13 and 14
depend on no optional field and are always drawn.

**Flow health**

1. Aging work in progress: open tickets, days in current status, descending.
2. Created versus closed per week, with a net backlog line.
3. Cumulative flow diagram, reconstructed from `status_durations`.
4. Cycle time scatter with 50th and 85th percentile lines.
5. Time in status per issue type.

**Reporting outward**

6. Delivered versus open per `fixVersion`.
7. Per epic: tickets done over total.
8. Ticket type mix per month.

**Retro**

9. Rework: backward transitions per sprint.
10. Sprint carry-over: tickets with `ordinal > 1`.
11. Cycle time distribution per sprint.
12. Story points versus actual cycle time, scatter. Tests whether the estimates
    carry information. Conditional on the null rate.

**People**

13. Throughput per person per week, as small multiples.
14. Review load: authors of transitions out of the review status.
15. Handoff matrix: assignee at first in-progress versus assignee at close.
16. Story points closed per person. Conditional on the null rate.

Median cycle time per person is deliberately omitted. It reads as a speed ranking
while actually measuring ticket mix, and charts 1 and 4 already answer the
underlying question without inviting that reading.

Per-person charts use small multiples rather than one ranked bar chart. The data
is the same; a leaderboard is not.

## Rendering

Inline SVG generated from Python. No JavaScript, no vendored chart library, no
CDN. The aggregates are a few hundred numbers, and bars, lines, stacked areas and
scatter are roughly 60 lines of SVG generation each. The output stays printable,
diffable and mailable for years.

If brushing or zoom on the scatter is ever genuinely wanted, that is the moment
to vendor uPlot (40KB, MIT), and not before.

The `dataviz` skill is to be read before the first line of chart code, for
palette, axis and accessibility decisions. Light and dark both matter, since the
file is opened in a browser.

## Testing

One `test_urd.py`, assert based, no framework.

Fixtures are hand written synthetic issue JSON covering a reopened ticket, a
ticket that skipped in-progress, and a ticket carried across two sprints.

The checks that matter, because this is where the logic is non-trivial:

- `status_durations` sums to the wall clock span of the issue.
- Rework count matches a hand computed value on the reopened fixture.
- A ticket that never entered in-progress is excluded from cycle time and appears
  in the coverage denominator.
- Carry-over detection on the two sprint fixture.
- The sync rule: an unchanged `updated` value produces zero fetches.

`ruff` runs clean before and after every change.

## Risks

| Risk | Mitigation |
| --- | --- |
| Story Points field absent, renamed or unpopulated | Resolved by name, null rate measured and reported, dependent charts render conditionally |
| Sprint field id differs per board or project | Resolved by name; `derive` reports how many issues had no sprint field at all |
| `STATUS_ORDER` misses a status, distorting rework | Unknown statuses rank last and are printed by `derive` |
| Enhanced JQL search endpoint changes pagination | Only two endpoints are used, both stable; failure is loud and resumable |
| Backfill hits a rate limit | Retry once, record in `sync_errors`, resume by re-running |
| Report read as precise when coverage is partial | Coverage denominator per chart, threshold warning strips, sync timestamp in the header |
| Work in the project without the component set is invisible | Measurable by comparing the headline count against a project wide count. Component hygiene is a team habit the tool depends on and cannot fix |
| Real names or ticket keys committed by accident | Output, database and captured responses gitignored from the first commit; fixtures synthetic; no instance specific defaults in source |

## Out of scope

- Following people across projects. Scope is project plus component, nothing
  else. See "Why scope is not follow the people".
- Any server, live query surface or scheduled run.
- Burndown and velocity charts, which Jira already draws.
- Writing to Jira. The tool is read only.
- Logged-time charts, replaced by cycle time. The field is fetched anyway.
- Jira Server and Data Center. Cloud REST v3 only.
- `RELEASING.md`, until there is something to release.
